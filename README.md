# Сайт контролируемой продажи счетчиков газа

Реализация ТЗ (редакция 6 от 06.10.2026). Интерфейсы:

- **Покупатель** (`/`, без авторизации): каталог, проверка права на покупку по ИИН и последним 6 цифрам номера ТУ с капчей, выбор точки выдачи, предупреждение, заказ с QR-кодом и PDF.
- **Продавец** (`/staff`): поиск заказа по QR (камера смартфона), номеру или ИИН; подтверждение оплаты фотографией кассового чека (JPEG до 500 КБ, сжатие на телефоне); чек-лист выдачи; серийный номер (ввод или штрих-код); доверенность; возврат (с возвратом исправного счетчика в остаток); отчеты и реестр продаж своей точки с выгрузкой в Excel; смена логина и пароля.
- **Финансист** (`/staff`): только просмотр и выгрузка отчетов — отчеты, реестр продаж, остатки и журнал движения; изменения запрещены на сервере.
- **Администратор** (`/staff`): отчеты, реестр продаж с фильтрами и выгрузкой в Excel, остатки по точкам (приход, корректировка, журнал движения), точки продаж, сотрудники (продавцы и финансисты), товарные карточки с фото, загрузка базы ТУ из папки, журнал действий, настройки (продажа юрлицам, учет остатков, порог «мало товара»), постоянный QR-код сайта и плакат A4.

## Стек

| Слой | Технология |
|---|---|
| Сервер | Node.js 22, Express 5 |
| База данных | PostgreSQL 15+ |
| Фронтенд | HTML, CSS, JavaScript без сборки; шрифт Onest и сканер html5-qrcode хранятся локально — внешних запросов нет |
| PDF, QR | pdfkit, qrcode (шрифт DejaVu с кириллицей) |
| Excel | exceljs (чтение реестров 1С, выгрузка отчетов) |

## Запуск через Docker (рекомендуется)

```bash
cp .env.example .env        # заполнить APP_SECRET, DB_PASSWORD, ADMIN_INITIAL_PASSWORD
docker compose up -d
```

Приложение слушает `127.0.0.1:3000`; наружу его публикует nginx с HTTPS (`deploy/nginx.conf`). HTTPS обязателен: без него браузер не даст доступ к камере для сканирования QR и штрих-кодов.

## Запуск без Docker

```bash
npm ci --omit=dev
cp .env.example .env        # указать DATABASE_URL на свой PostgreSQL
npm start
```

Демо-точки и демо-товары: `npm run seed` (база ТУ не заполняется).

Сброс забытого пароля администратора: `docker compose exec app node scripts/reset-admin.js admin`.

Подробная инструкция по развертыванию на сервере — отдельный документ «Инструкция по развертыванию».

## Первый вход

1. При первом запуске создается администратор из `ADMIN_LOGIN` / `ADMIN_INITIAL_PASSWORD`.
2. Войдите на `/staff`. Система потребует сменить временный пароль.
3. Создайте точки продаж, товары и продавцов. Для продавца система генерирует временный пароль; он показывается один раз, продавец меняет его при первом входе.
4. Загрузите базу ТУ: «База ТУ» → «Выбрать папку».

## Требования к паролю сотрудников

Проверяются на сервере; в форме смены пароля выполнение требований показывается по мере ввода.

- длина от 10 до 64 символов (`PASSWORD_MIN_LENGTH`);
- заглавная и строчная буквы (латиница или кириллица), цифра, спецсимвол;
- без пробелов, не содержит логин, не более двух одинаковых символов подряд;
- не содержит распространенных слов (password, qwerty, admin, qazaqgaz и т. п.);
- не совпадает с 3 предыдущими паролями;
- действует 90 дней (`PASSWORD_MAX_AGE_DAYS`), затем система требует смену;
- временный пароль (новый продавец, сброс администратором) нужно сменить при первом входе;
- после смены пароля остальные сеансы пользователя завершаются;
- хранение — только хэш bcrypt.

Логин: 3–32 символа, латинские буквы, цифры, точка, дефис, подчеркивание.

## Защита

- **Проверка покупателя:** капча при каждой проверке; после 5 неудачных попыток подряд проверка по ИИН блокируется на 60 минут независимо от того, есть ли ИИН в базе; отдельный лимит по IP. Сообщение об ошибке общее, без указания неверного поля. Все попытки пишутся в `check_log`.
- **Вход сотрудников:** капча; 5 неудачных попыток — блокировка учетной записи на 60 минут; лимит по IP. Сеанс — 10 часов, завершается после 60 минут бездействия.
- **Данные:** покупатель видит только имя с первой буквой фамилии и адрес; полные ФИО и ИИН — только продавцу и администратору. Заказ открывается по секретной ссылке (токен в QR).
- **Правило «одно ТУ — один счетчик»** закреплено уникальным индексом в БД (не обойти даже одновременными запросами). Неоплаченный заказ отменяется через 2 часа (`ORDER_TTL_MIN`), ТУ освобождается.
- Cookie `HttpOnly`, `Secure`, `SameSite=Strict`; проверка заголовка против CSRF; CSP и прочие заголовки (helmet); параметризованные SQL-запросы.
- **Журнал действий:** вход, выдача, возврат, оплата, изменения справочников, загрузка ТУ, выгрузка отчетов.

## Загрузка реестра ТУ

Принимаются выгрузки из 1С «Технические условия» в формате `.xlsx` — до 50 файлов за раз. Колонки ищутся по заголовкам: «Абонент», «Адрес», «Дата», «ИНН», «Номер», «Расход газа». Филиал берется из строки «Организация: …» в шапке. Строка «Итого» пропускается.

Из адреса удаляются «Республика Казахстан,» и «ЖИЛОЙ ФОНД». Ключ записи — номер ТУ: повторная загрузка не создает дублей. Строки с ошибками (ИИН не из 12 цифр, нет номера и т. п.) не загружаются и перечисляются в итогах.

## Оплата

По умолчанию оплату подтверждает продавец: вводит номер кассового чека, после этого заказ становится «Оплачен» и доступен к выдаче.

Если касса может передавать оплату автоматически, задайте `POS_API_KEY` и настройте кассу на запрос:

```
POST /api/pos/payments
X-Api-Key: <POS_API_KEY>
{ "qr": "QGA:100001:…", "amount": 54000, "receiptNumber": "000123" }
```

## Учет остатков

Включается администратором в разделе «Настройки» после внесения прихода по точкам. Доступно к заказу = на складе − в брони (заказы «Ожидает оплаты» и «Оплачен»). Заказ проверяет остаток под блокировкой строки, поэтому последнюю штуку нельзя продать дважды даже при одновременных заказах. Выдача списывает 1 шт.; при возврате исправный счетчик возвращается в остаток, неисправный — нет. Все движения пишутся в журнал.

## Настройки по открытым вопросам ТЗ

| Переменная | Назначение |
|---|---|
| `ALLOW_LEGAL_ENTITIES=false` | начальное значение настройки «Разрешить продажу юридическим лицам»; дальше администратор меняет ее в кабинете |
| `MAX_GAS_FLOW=6` | не продавать по ТУ с расходом газа выше значения |

## Хранение данных и резервные копии

Все данные, включая фото товаров, хранятся в PostgreSQL. Сервер должен находиться на территории РК (Закон РК «О персональных данных и их защите»).

Порт БД наружу не публикуется. Для ежедневного резервного копирования используйте `scripts/backup.sh` через cron; копии хранятся 30 дней.

## Обновление из GitHub

- `.github/workflows/ci.yml` — при каждом изменении GitHub Actions запускает автотесты с PostgreSQL и проверяет сборку Docker-образа.
- Версия выпускается тегом `vX.Y.Z` на коммите в `main`, у которого тесты прошли: `git tag -a v1.1.0 -m "описание" && git push origin v1.1.0`.
- `scripts/auto-update.sh` + `deploy/gasmeter-update.timer` — сервер каждые 5 минут проверяет новую версию и ставит ее в окно обновлений (по умолчанию 20:00–08:00). Перед установкой — резервная копия базы, после — проверка `/api/health`; при сбое — автоматический возврат на предыдущую версию, и сбойная версия больше не ставится автоматически.
- Срочная установка: `scripts/auto-update.sh --now`. Откат на конкретную версию: `scripts/auto-update.sh v1.0.0`. Журнал: `logs/update.log`.
